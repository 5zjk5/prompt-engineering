# Project Analyzer — Agent 架构技术专著

## 定位：写一本书，不是写一份文档

输出物是**一本以某个开源项目为贯穿案例的技术专著**。读者读完后应能做到两件事：一是系统性地学会 Agent / RAG 这套技术体系，二是把书中讲到的方案直接当作设计自己系统时的参考。

这决定了两者体例的根本差异：

| | 项目梳理文档 | 技术专著（本技能） |
|---|---|---|
| 组织依据 | 本项目有哪些模块 | 知识体系怎么递进 |
| 项目角色 | 唯一主体 | 贯穿全书的案例 |
| 章节标题 | 「工具系统」「记忆机制」 | 「为什么工具多了模型就选不准」 |
| 讲法 | 它做了什么 | 概念 → 原理 → 有几种做法 → 它选了哪种 → 代价 |
| 读者收益 | 知道这个项目长什么样 | 学会一类问题的解法，并知道何时该用 |

**判断内容取舍的标准**：

> 读者合上这一章，能不能独立回答"这个技术点是什么、为什么需要、有哪几种做法、我该选哪个"？

而不是"这个项目有哪些文件"。

## 产出物

- **文件名**：`【仓库名】.md`（如 `agentrack.md`）。不加"项目梳理"后缀、不加日期前缀。
- **一级标题**：`# 【仓库名】`，下一行副标题点明本书视角，如 `> 以 X 为案例的 Agent 架构实现剖析`。
- **篇幅**：15,000–30,000 字。核心章每章 1,500–2,500 字。
- **落盘方式**：先写全书骨架（卷首 + 全部章节标题 + 各章导读），再**逐章追加填充**。不要试图一次性输出全文——超长单次输出会被截断，且难以保持质量。
- **入库**：本技能只输出文件。不执行上传，不追问知识库目标。

## 触发条件

**触发**：
- 用户给出 GitHub 地址或本地仓库路径，要求梳理 / 分析 / 讲透这个项目的技术实现
- 用户想通过某个开源 Agent 项目学习 Agent 架构
- 用户想要一份能当参考手册用的 Agent 技术资料

**不触发**：
- 只问某个具体函数怎么实现（直接回答）
- 要求在仓库里改代码、修 bug、做 code review
- 只要一份几百字的项目简介

## 全书的六要素体例

每一章（收束章除外）都必须覆盖以下六个要素。缺任何一条，这一章就不成立——缺「原理」变成功能清单，缺「对比」变成项目广告，缺「权衡」变成教程抄写。

| 要素 | 回答什么 | 常见错误 |
|---|---|---|
| **① 概念与问题** | 这东西是什么？没有它会怎样？ | 直接跳到实现，读者不知道在解决什么 |
| **② 原理** | 为什么必须这么设计？底层机制是什么？ | 只描述现象，不解释成因 |
| **③ 业界做法对比** | 有哪几种主流方案？各自失效场景？ | 只讲本项目那一种，读者以为它是唯一解 |
| **④ 本案例实现** | 这个项目选了哪种，怎么落地，参数阈值多少 | 与 ③ 脱节，看不出选择 |
| **⑤ 权衡与边界** | 好处、坏处、什么场景别用 | 只写优点，或写"各有优劣"这种无信息量的话 |
| **⑥ 小结** | 3–5 条可带走的结论 | 复述原文，没有提炼 |

章节顺序可按内容需要调整（如把「对比」插在「原理」前后），但这六个要素不能少。

## 全书章节架构

六部分十四章。**核心章必写**，其余按项目实况取舍。

### 卷首（必写）

- 本书讲什么、适合谁读、怎么读（三条阅读路径：只想了解该项目 / 想学 Agent 架构 / 只想查某个机制）
- 案例项目概况：GitHub 地址、主语言、一句话定位
- **代码地图**：只列本书会引用的 8–12 个文件及其职责，让人知道从哪读起。**不是完整目录树**

### 第一部分 认识这个系统

| 章 | 标题 | 核心内容 | 分级 |
|---|---|---|---|
| 1 | 案例项目全景 | 问题域、系统形态、一次请求的鸟瞰、设计取向总表 | 核心 |
| 2 | Agent 范式与选型逻辑 | ReAct / Plan-Execute / Reflection / 图编排 / 纯 Workflow，选型矩阵与本案例的选择理由 | 核心 |

| 4 | 上下文工程 | token 经济学、注意力衰减、组成与优先级、压缩四法、触发与保留策略、上下文隔离 | 核心 |

### 分级处理规则

| 分级 | 处理方式 |
|---|---|
| **核心** | 完整六要素，本案例实现详写，配流程图 |
| **按实况·项目有实现** | 完整六要素，本案例实现详写，配流程图 |
| **按实况·项目无实现** | 保留章节，①②③⑤⑥ 照写（用业界通用知识），④ 写成本项目为何不做、用什么替代、什么条件下才需要补上 |
| **与本书主题无关** | 删除，不保留空章节 |

## 事实来源标注规范

**这是硬约束**。用户会核对，编造一处就毁掉整份材料的可信度。

| 标记 | 含义 | 写法 |
|---|---|---|
| 【代码】 | 来自仓库源码 | 直接给 `路径/文件.py` → `函数名()`，无需额外标记 |
| 【业界】 | 通用技术知识，非本项目特有 | 句末标注 `【业界】`；引用具体产品/论文时给出名称 |
| 【推断】 | 读代码得出的推测，未经直接验证 | 标注 `【推断，未在代码中确认】` |

补充规则：
- 项目中不存在的东西，绝不写成本项目的实现
- 业界对比部分允许用 WebSearch 补充最新做法，但必须标注 `【业界】`，且不写具体版本号/发布日期
- 数字（阈值、轮数、token 上限）必须与代码一致；代码里是配置项而非硬编码的，写"默认 X，可配置"

## 写作流程

### 阶段一：读模板

读取 `references/agent-book-template.md`，获取各章的知识点清单、章内骨架样例、图表与代码呈现规范。

### 阶段二：把握案例项目

1. 读 README / docs / examples，判断项目类型与形态
2. 用「代码探索策略」中的锚点表定位核心文件
3. 建立**代码地图**：本书会引用的 8–12 个文件及职责
4. 形成架构假设清单：猜测的范式、主链路、机制分布 + 待验证疑点

### 阶段三：定章节目录

根据项目实况，对 14 章逐条判定：核心 / 有实现 / 无实现 / 删除。产出一份章节目录，标注每章预计篇幅与要写的知识点。

**这一步必须显式完成**。直接开写会导致章节失衡——前面几章写太细，后面草草收尾。

### 阶段四：落盘骨架

一次性写入文件骨架：卷首 + 全部章节标题与导读 + 附录标题，正文留占位。骨架先落盘，后续逐章填充，中途中断也不丢结构。

### 阶段五：逐章撰写

按章节顺序写，**每章一次追加**（用 Edit 替换该章的占位内容）。每章严格走六要素。

写每章前先问三个问题：
1. 这一章要让读者学会解决什么问题？
2. 业界的几种做法我能不能说清各自失效场景？
3. 本案例的选择在这个对比里处于什么位置？

### 阶段六：通篇校订

全书写完后回头检查：
- 术语是否全文一致（同一概念不要换三种说法）
- 章节间交叉引用是否正确（"见 4.3 节"这类）
- 有无重复讲述同一机制
- 有无【】占位符残留
- 有无章节失衡（某章明显比其他章单薄）

### 阶段七：交付

确认文件路径与文件名，报告篇幅与章节结构，说明哪些章因项目未涉及而作了简化处理。不执行上传。

### 探索纪律

- 大仓库用 Explore 子代理并行探索，围绕具体架构问题提问，不做无目的通读
- 精读范围限定：主链路 + 各机制核心文件
- **不读**：前端界面、管理后台、部署脚本、测试用例、业务 CRUD 逻辑
- 读到的每个关键结论随手记下文件路径，避免写作时回查

### 深度要求

| 对象 | 深度 |
|---|---|
| 主链路 | 到函数级，每个环节配图 |
| 各机制 | 到机制级——策略、阈值、算法、失效条件；流程图要画全，代码不逐行 |
| 工具实现 | 用途 + 关键参数 + 执行方式 |
| 配置项 | 只在影响架构时提及具体值 |

## 输出质量要求

- **教材感**：每章读完要知道"为什么"，不能只留"是什么"。原理讲不透的章节，宁可压缩篇幅也不要堆砌。
- **对比意识**：凡有多种做法的地方，必须给出对比表与各自失效场景。写"各有优劣"而不说清何时用哪个，视为不合格。
- **案例贯串**：每章都要落到本案例上——选了哪种、在哪实现、参数多少。纯理论章节不超过 2 章。
- **诚实**：严格按「事实来源标注规范」区分代码事实、业界知识、推断。
- **流程图**：主链路每个环节、每个机制单元必须配图。图是理解架构的主要载体，读者多数时候先看图。
- **可查性**：关键结论附 `文件路径 → 函数名()`，让读者能回到源码验证。
- **不注水**：不写"综上所述""值得注意的是"这类填充句；不为凑篇幅重复已讲内容。
