# 专著模板：卷首 + 十四章大纲 + 呈现规范

本文件是撰写 Agent 架构专著的完整作业指引。**逐章大纲里列出的知识点，是该章必须讲到的下限**——可以扩展，不能遗漏。

### 完整示例：第 4 章的开头两节

以下示范"概念 → 原理"怎么写才算讲透。注意它没有直接讲项目代码，而是先把问题立起来。

```markdown
## 4. 上下文工程：Agent 最贵的资源

> **本章导读**：一个 Agent 跑到第 30 轮时，为什么开始忘掉最初的需求？本章拆解上下文
> 从"能装多少"到"该装什么"的完整策略，读完你能为自己的系统设计一套压缩方案，
> 并知道每种方案的失效边界。

### 4.1 上下文不是越大越好

【现象】把对话历史全量塞给模型，成本线性上涨，但答题质量不一定上升，甚至下降。

【原因，三层】
1. **成本与延迟的硬约束**：token 数直接决定单次调用成本与首 token 延迟。多轮 Agent 每轮
   都要重发全部历史，总成本是轮数的平方级增长。
2. **注意力衰减**：模型对长上下文中间位置的召回显著弱于首尾，这不是提示词能修补的
   缺陷，而是位置编码与训练分布共同作用的结果【业界】。
3. **噪声稀释**：无关的历史消息会与当前任务争夺注意力，工具返回的大段原始输出尤其
   有害——它通常占 token 的 80% 以上，但信息密度极低。

【推论】上下文管理的目标不是"塞更多"，而是"在有限预算下最大化与当前决策相关的信息
密度"。这一定义决定了后续所有策略的方向。

### 4.2 压缩的四种基本手法

【为什么只有四种】压缩的本质是丢弃信息，而丢弃的方式只有四类：按位置丢、按摘要丢、
按结构丢、移出窗口。……

```

**注意这段的写法特征**：先给现象，再给三条成因并标注哪些是业界结论，最后从成因推出设计目标。这是教材写法，与功能清单式写法的区别就在这里。

## 三、十四章逐章大纲

### 第 1 章 案例项目全景

**本章导读要立的问题**：这个项目在一个什么样的技术位置上？它替代了什么？

必讲知识点：
- **问题域**：它替代了什么人工流程？不用 Agent 而直接调 LLM 会差在哪？把问题具体化到场景，不写行业趋势
- **系统形态**：CLI / 服务 / 库 / 插件；单 Agent 还是多 Agent；同步还是流式；有无界面
- **一次请求的鸟瞰**：从用户输入到最终输出，一张总图
- **设计取向总表**：每个关键维度上的选择 + 被放弃的备选 + 代价（这张表是全书的纲领，后续每章都是它的展开）
- **代码地图**：8–12 个文件，见卷首

必讲的对比：
- 同类项目在本项目所处位置上的差异【业界】（可选，不要写成竞品评测）

本章陷阱：写成 README 摘要；罗列功能清单；开头就贴目录树。

### 第 2 章 Agent 范式与选型逻辑

**本章导读要立的问题**：ReAct 凭什么成为默认范式？它在什么情况下会崩？

必讲知识点：
- **从 prompt 到 agent 的三要素**：循环、工具、状态。缺任一个就不是 agent
- **ReAct**：Reasoning + Acting 交替的结构；为什么把推理外化成可观察的文本步骤有效（错误可归因、可中断、可人工纠偏）；它的失效模式——长任务中推理链发散、重复试错、陷入局部最优
- **Plan-and-Execute**：规划与执行分离；好处是全局视野与可审查的计划；坏处是计划僵化、需要重规划机制、token 双倍
- **Reflection / Reflexion**：自我批评回路，怎么触发、批评什么、如何避免无限反思
- **图编排（Workflow Graph）**：节点 + 边 + 条件分支；把不确定性收敛到少数节点；可观测性与可测试性的收益
- **纯 Workflow（不用 agent）**：什么时候固定流程比 agent 更好——步骤可枚举、错误代价高、需要确定性
- **选型矩阵**：可预测性 × 灵活性 × 调试成本 × token 成本，四维对照
- **本案例的选择**：选了哪种、代码里怎么体现、为什么在它的场景下这个选择成立

本章陷阱：把"用了某个框架"当成范式；只讲 ReAct 一种；不讲反范式（何时不该用 agent）。

---

### 第 3 章 主循环的工程实现

**本章导读要立的问题**：一个 while 循环看起来简单，为什么工程上到处是坑？

必讲知识点：
- **循环骨架**：伪代码级的最小骨架（取上下文 → 调模型 → 判断 → 执行工具 → 回灌）
- **单轮状态构成**：消息列表、步数、终止标记、工具结果、累计 token
- **消息角色与顺序**：system / user / assistant / tool 的排列规则，以及顺序错了会怎样
- **终止条件设计**：模型自决（end_turn）vs 外部计数 vs 超时 vs 无进展检测 vs 重复动作检测。为什么四道闸门都不能少
- **并行工具调用**：同一轮多个 tool_call 如何并发、结果如何保序、部分失败怎么表达
- **异常分类**：模型错误 / 工具错误 / 解析错误 / 超时，四类各自的处理方式
- **中断与恢复**：用户打断后状态如何保持一致
- **本案例逐环节拆解**：每个环节配 text 代码流程 + mermaid 环节图

必讲的对比：
| 方案 | 做法 | 优点 | 失效场景 |
|---|---|---|---|
| 模型自决终止 | 靠 finish_reason | 自然、灵活 | 模型误判、陷入循环 |
| 计数上限 | max_iterations | 确定性兜底 | 正常长任务被腰斩 |
| 无进展检测 | 比较连续轮次的动作 | 抓真死循环 | 误杀探索性任务 |

本章陷阱：只靠模型决定何时停；把重试当成异常处理的全部。

### 第 4 章 上下文工程

**本章导读要立的问题**：为什么"多给点上下文"反而是错的？

必讲知识点：
- **token 经济学**：成本随轮数平方增长；首 token 延迟；窗口上限不是可用的工作预算
- **注意力衰减与 lost in the middle**：中间位置召回弱【业界】；对策略的含义——重要信息放首尾
- **上下文组成与优先级**：系统提示 > 当前任务目标 > 最近若干轮 > 早期摘要 > 检索结果；冲突时谁让步
- **压缩四法**：
  1. 截断（按位置/按类型丢）
  2. 摘要（LLM 压缩，有漂移风险）
  3. 结构化抽取（只保留决策要点，损失叙事但信息密度高）
  4. 外部化（移到文件/记忆，需要时再检索回来）
- **触发策略**：阈值触发 / 轮次触发 / 事件触发（如工具返回超长时单独压缩）
- **保留策略**：永不压缩的部分——系统提示、原始任务目标、已确认的关键结论
- **压缩的风险**：信息损失、摘要漂移（多次摘要后失真）、压缩后与工具状态不一致
- **上下文隔离**：子 Agent 各有窗口，代价见第 11 章
- **本案例**：压缩在哪实现、阈值多少、保留什么、失败怎么回退

必打的对比表：
| 压缩法 | 信息保留度 | token 收益 | 实现复杂度 | 失效场景 |
|---|---|---|---|---|
| 截断 | 低 | 高 | 低 | 丢掉仍在被引用的前提 |
| LLM 摘要 | 中 | 中 | 中 | 多轮摘要后失真 |
| 结构化抽取 | 高（决策）/低（细节） | 高 | 高 | 任务需要原文细节 |
| 外部化 + 检索 | 高 | 高 | 高 | 检索不回来 |

本章陷阱：以为压缩免费；只讲一种压缩法；不讲保留策略。

### 第 5 章 工具系统

**本章导读要立的问题**：工具是给模型用的接口，为什么"写清楚"比"写得多"重要？

必讲知识点：
- **工具即接口**：模型只能通过 schema 理解能力，schema 就是全部
- **schema 设计**：命名（动词+对象，避免泛化词）、描述、参数类型、必填项、枚举约束
- **description 工程**：写清四件事——做什么、什么时候该用、什么时候不该用、返回什么。少写四件事——实现细节、内部参数、与其他工具的关系推理、营销式描述
- **参数设计**：枚举优于自由文本；扁平优于嵌套；单位与格式要写进描述
- **注册与发现**：装饰器自动注册 / 显式清单 / 目录扫描 / 运行时发现，各自的维护成本
- **工具选择准确率**：工具数量与选择准确率的反向关系【业界】；由此引出按需加载
- **按需加载三种做法**：工具检索（用描述做语义匹配）、分层（先选类别再选工具）、动态暴露（按任务阶段切换工具集）
- **并行与依赖**：哪些工具能并发、有副作用的如何串行
- **返回结果设计**：结构化优先、长结果截断、错误信息要能被模型理解并纠正（而非堆栈）
- **执行边界**：沙箱/本地进程、超时、资源上限、幂等性、副作用
- **Skill / 插件封装**：Skill 是工具之上的编排层还是提示词包？发现机制如何、与普通工具的区别
- **本案例**：注册机制、工具清单（按类分组不逐个罗列）、选择与调度策略、执行环境

必打的对比表：
| 注入方式 | 适用工具量 | 优点 | 代价 |
|---|---|---|---|
| 全量注入 | < 20 个 | 简单、无额外调用 | 工具多时选择准确率下降 |
| 检索式加载 | > 50 个 | 上下文省、准确率高 | 多一次检索、可能漏选 |
| 分层加载 | 20–50 个 | 折中 | 需要人工分层 |

本章陷阱：把工具当函数库写；只讲注册不讲选择；不写返回结果设计。

### 第 6 章 提示词设计

**本章导读要立的问题**：同样一段提示词，为什么换个写法行为就变了？

必讲知识点：
- **分层结构**：角色与能力边界 → 工作流程 → 硬约束 → 输出格式。层次清楚才能定位问题
- **约束的写法**：正面表述优于禁止性罗列；约束必须可执行、可检验；给反例比给形容词有效
- **few-shot 的取舍**：示例数量与过拟合风险；示例要覆盖边界情况而非典型情况
- **输出格式控制三档**：prompt 约束 → 结构化输出模式（JSON mode）→ schema 强制（function calling / tool schema）。可靠性依次上升，灵活性依次下降
- **解析与修复**：解析失败的三种处理——原样重试、带错误提示重试、格式化修复
- **提示词与上下文的耦合**：提示词里引用的变量从哪来、缺失时怎么办
- **本案例关键 prompt 解剖**：骨架树（层级 + 变量来源 + 约束），说明哪几条约束是真正防跑偏的

必打的对比表：
| 格式控制 | 可靠性 | 灵活性 | 成本 |
|---|---|---|---|
| prompt 约束 | 低 | 高 | 低 |
| JSON mode | 中 | 中 | 低 |
| schema 强制 | 高 | 低 | 中（部分 provider 额外计费） |

本章陷阱：把约束堆成 wishlist；只贴提示词原文不做解剖。

### 第 7 章 记忆与状态持久化

**本章导读要立的问题**："记住"这件事，到底该记什么、记在哪、什么时候忘？

必讲知识点：
- **三层记忆**：工作记忆（当前轮） / 会话记忆（本次对话） / 长期记忆（跨会话）
- **写入策略**：什么值得记（用户偏好、已确认事实、任务状态 vs 寒暄）；何时写（即时 / 轮末 / 会话结束）；写之前要不要先判断重复
- **存储形态与取舍**：消息表 / 摘要文本 / 向量库 / 知识图谱 / 文件。各自的检索能力与维护成本
- **检索与重排**：长期记忆怎么被召回，按时间、按相关性还是混合
- **遗忘机制**：TTL、重要性衰减、容量上限淘汰
- **冲突消解**：同一事实多次写入不一致时以谁为准
- **跨会话恢复**：读什么、按什么顺序回灌、有无一致性校验
- **本案例**：用了哪几层、存在哪、恢复流程

必打的对比表：
| 存储形态 | 适合记什么 | 检索能力 | 代价 |
|---|---|---|---|
| 消息表 | 原始对话 | 按会话/时间 | 语义检索弱 |
| 摘要文本 | 长期要点 | 弱 | 失真 |
| 向量库 | 事实片段 | 语义 | 需维护、无结构 |
| 知识图谱 | 实体关系 | 结构化推理 | 构建成本高 |

本章陷阱：把所有消息当记忆；只讲存不讲取和忘。

### 第 8 章 RAG 检索增强

**本章导读要立的问题**：RAG 解决的到底是"不知道"还是"记不准"？

必讲知识点：
- **RAG 的边界**：解决私有知识与时效性、提供可溯源引用；不解决推理能力不足、不解决知识冲突、不解决"检索不到"
- **切分**：固定窗口 / 递归分隔 / 语义切分 / 结构感知（按标题、按代码块）；父子块策略；重叠比例的取舍
- **向量化**：embedding 模型选择维度（通用 vs 领域）、归一化、批量与成本
- **索引**：ANN 近似检索（HNSW / IVF）的精度-速度权衡
- **召回**：稠密检索 / 稀疏检索（BM25）/ 混合 + 融合（RRF）/ 多查询扩展 / HyDE
- **重排**：cross-encoder、LLM rerank、MMR 去冗余；重排的收益与延迟代价
- **注入**：放在上下文的什么位置（避开中间）、放几条、是否标注引用来源
- **评测**：召回率/精确率、忠实度（答案是否落在检索内容内）、answer relevance；如何构造评测集
- **Agentic RAG**：把检索做成工具，由模型决定检索什么、检索几次；与固定 RAG 的差异、成本、可控性
- **本案例**：有实现则详写链路；无实现则说明为何不需要、什么条件下要补

必打的对比表：
| 方案 | 检索时机 | 优点 | 失效场景 |
|---|---|---|---|
| 固定 RAG（每轮预检索） | 每轮固定 | 简单、可预测 | 问题不需要检索时浪费、复杂问题一次检索不够 |
| Agentic RAG（检索作为工具） | 模型决定 | 灵活、可多轮 | 成本高、可能不检索、延迟不可控 |

本章陷阱：把 RAG 等同于向量检索；只讲召回不讲重排与评测。

### 第 9 章 模型接入层

**本章导读要立的问题**：为什么换一个模型，整个系统就可能不工作？

必讲知识点：
- **provider 差异**：API 形态、tool calling 的支持粒度与格式差异、上下文窗口、限流策略、计费口径
- **抽象层设计**：统一接口（LiteLLM 类）vs 原生 SDK + adapter。抽象层的收益与代价——会吃掉 provider 特有的能力
- **流式**：SSE 分块、增量工具调用参数的聚合、流式下的错误处理、UI 如何渲染
- **结构化输出**：与第 6 章呼应，从模型侧的角度讲
- **多模型路由**：按任务复杂度 / 按成本 / 按能力；路由错误的代价
- **重试**：指数退避、抖动、幂等前提、哪些错误不该重试
- **降级**：备用模型、简化 prompt、缓存命中
- **限流与并发**：并发控制、队列
- **token 统计与成本归因**：按轮、按阶段、按功能统计，才能定位成本黑洞
- **本案例**：抽象层选择、路由策略、降级链路

本章陷阱：抽象层吃掉特性；只讲调用不讲降级与成本。

---

### 第 10 章 MCP 与外部能力接入

**本章导读要立的问题**：既然已经有 function calling，为什么还需要一个协议？

必讲知识点：
- **M×N 问题**：M 个模型客户端 × N 个工具服务，没有标准协议时需要 M×N 套适配；MCP 把它降为 M+N
- **协议构成**：传输层（stdio / SSE / streamable-http）；能力协商（初始化握手）；原语（tools / resources / prompts 三类各自语义）
- **客户端实现**：建连 → 能力协商 → list_tools → schema 转换 → 并入本地注册表 → call_tool → 生命周期与重连
- **服务端视角**：如何暴露工具、如何声明 schema、如何返回结构化结果与错误
- **与内置工具的差异**：动态发现（非编译期确定）、进程隔离（独立进程/远端）、延迟（多一次 IPC/网络往返）、失败面更大
- **命名空间与冲突**：服务名前缀、同名工具消歧
- **其他外部集成**：代码执行沙箱、浏览器自动化、检索服务、第三方 API——接入方式的共性与各自失败处理
- **本案例**：是否用 MCP、配置在哪、发现时机、与内置工具如何合并

必打的对比表：
| 方案 | 接入成本 | 动态性 | 延迟 | 隔离性 |
|---|---|---|---|---|
| 内置工具 | 低（同进程） | 无（需重新部署） | 最低 | 无 |
| MCP | 中（一次协议实现） | 高（运行时发现） | 中 | 进程/网络隔离 |

本章陷阱：把 MCP 当成万能插件系统；只讲客户端不讲协议动机。

---

### 第 11 章 多 Agent 协作

**本章导读要立的问题**：什么时候多 Agent 真的比单 Agent 强，什么时候只是把问题变复杂？

必讲知识点：
- **动机**：上下文隔离（各自窗口不被污染）、角色专精（提示词更聚焦）、并行（可同时推进）、可测试（单个 agent 可独立验证）
- **拓扑**：主从（supervisor）/ 层级 / 平级协商 / 流水线 / 辩论。各自适用场景
- **通信方式**：共享上下文 / 消息传递 / 文件交接 / 结构化 handoff（带状态转移）。信息损失逐级递增
- **调度**：静态分工 vs 动态派发；派发决策由谁做
- **上下文隔离的代价**：主 Agent 看不到子 Agent 的过程，只能看结论；结论质量不可控；重复劳动
- **冲突与收敛**：多 Agent 结论矛盾时的裁决机制
- **常见失败模式**：责任扩散（都以为别人做了）、无限委派、成本爆炸、死锁（互相等待）
- **本案例**：角色划分、拓扑、通信、结果汇总

必打的对比表：
| 方案 | 上下文隔离 | 并行度 | 复杂度 | 适用场景 |
|---|---|---|---|---|
| 单 Agent + 多工具 | 无 | 工具级并行 | 低 | 任务链路短、上下文可控 |
| 多 Agent | 强 | 高 | 高 | 子任务独立、需要不同专长 |

本章陷阱：为多而多；不写失败模式。

---

### 第 12 章 长任务执行与可靠性

**本章导读要立的问题**：一个跑两小时的任务，中途崩了怎么办？

必讲知识点：
- **长任务的三个敌人**：上下文超限、状态丢失、时间与外部世界变化
- **任务分解与计划落盘**：任务清单外置为文件，为什么不能只存在上下文里
- **断点恢复**：checkpoint 的粒度选择（每步 / 每阶段 / 定时）；恢复时如何重建上下文
- **幂等与副作用**：哪些操作可重复执行、哪些必须做去重标记；重复执行的现实危害
- **人在回路**：审批点设计、打断后的状态一致性、纠偏机制
- **重试的边界**：哪些错误可重试、重试次数与总时长、重试放大的风险
- **进度可见性**：长任务如何向用户报告进度，避免黑盒
- **本案例**：有哪些可靠性机制、缺哪些

本章陷阱：把重试当万能；不区分可重试与不可重试。

---

### 第 13 章 评测与可观测性

**本章导读要立的问题**：Agent 输出每次都不一样，怎么判断它"行不行"？

必讲知识点：
- **为何难评测**：非确定性、多步复合误差、缺乏标准答案、成本高
- **评测维度**：任务成功率 / 步骤效率（几步完成）/ 成本 / 延迟 / 人工评分
- **离线评测集**：从真实任务采样、覆盖边界、定期回归
- **在线评测**：A/B、用户反馈信号、失败会话回捞
- **trace**：每一步的输入输出、工具调用参数与结果、token 消耗。没有 trace 就无法归因
- **成本归因**：按阶段/功能统计，找出成本黑洞
- **失败归因分类**：选错工具 / 参数不对 / 上下文丢信息 / 模型能力不足 / 环境问题。分类决定了优化方向
- **本案例**：有哪些可观测手段、评测做了什么

本章陷阱：只看最终答案对不对；不做归因分类。

## 五、呈现规范

### 图表

**mermaid**：
- 默认 `flowchart TD`；横向流程用 `flowchart LR`；状态机用 `stateDiagram-v2`
- 节点形状：`([起止])` 圆角、`[步骤]` 矩形、`{判断}` 菱形
- 节点内 `<br/>` 换行，第二行附函数名与文件位置
- 条件边写清判断条件，不写笼统的"是/否"
- 一张图只表达一个机制或一个环节；节点 8–15 个，超出拆成总览图 + 细节图
- 机制讲解类章节（第 2、4、8、11 章）可用示意图表达抽象关系，不必对应具体函数

**text 流程图**：
- `├→` `└→` 表层级，`←` 后标文件路径
- 每节点写「做了什么 + 调用的函数」
- 与同节 mermaid 互补：text 侧重函数调用与文件定位，mermaid 侧重分支走向

**必配图位置**：第 3 章每个环节、第 4 章压缩流程、第 5 章注册调用链、第 7 章恢复流程、第 8 章检索链路、第 9 章降级链路、第 10 章 MCP 发现、第 11 章拓扑、第 12 章恢复时序。没有实质分支的单步动作可只写文字。

### 代码片段

- 控制在 20 行内，只保留关键行，中间用 `# ...` 省略
- 片段前标注 `路径/文件.py`，片段后一句话说明这段在讲什么
- 只贴有讲解价值的代码：关键判断、阈值、schema 定义、prompt 结构。不贴样板代码

### 表格

- 所有对比（方案、存储形态、格式控制）必须用表格，不用长段落罗列
- 表头不超过 5 列；列多说明拆分维度

### 事实标记

- `【业界】`：通用技术知识，标注在句末
- `【推断，未在代码中确认】`：读代码得出的推测
- 来自代码的结论直接给 `路径/文件.py` → `函数名()`，不加标记

### 篇幅分配

| 部分 | 占比 | 说明 |
|---|---|---|
| 卷首 + 第 1 章 | 10% | 导航与全景 |
| 第 2–6 章（运行时内核） | 45% | 全书重心 |
| 第 7–13 章 | 35% | 按项目实况浮动 |
| 第 14 章 + 附录 | 10% | 收束 |

单章低于 1,200 字时，检查是否漏了六要素中的某一项。
